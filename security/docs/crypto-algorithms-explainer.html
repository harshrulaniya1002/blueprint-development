🔁 Symmetric Encryption Same Key

In symmetric encryption, the same secret key is used to both encrypt and decrypt data. It is fast and efficient, making it ideal for bulk data encryption. The primary challenge is key distribution — both parties must share the key securely beforehand.

✅ Advantages

  • Fast — hardware-accelerated (AES-NI)
  • Suitable for large data volumes
  • Simple key management for closed systems
  • Low computational overhead

❌ Disadvantages

  • Key distribution problem — how do you share the key securely?
  • Doesn't provide non-repudiation
  • Each pair of communicators needs a unique key
  • Key compromise breaks all past/future messages

🔓 Asymmetric (Public-Key) Encryption Key Pair

Asymmetric cryptography uses a mathematically linked key pair: a public key (freely shared) and a private key (kept secret). Data encrypted with the public key can only be decrypted with the corresponding private key, and vice versa.

✅ Advantages

  • Solves the key distribution problem
  • Enables digital signatures and non-repudiation
  • Foundation of PKI, TLS, SSH, PGP
  • Enables key exchange without pre-shared secret

❌ Disadvantages

  • Slow — 100–1000× slower than symmetric
  • Large key sizes (RSA 2048–4096 bit)
  • Vulnerable to quantum computers (Shor's algorithm)
  • Complex key management infrastructure (PKI)

How RSA Works (conceptually)

-- Key Generation --
Choose large primes p, q  →  n = p × q  (modulus)
φ(n) = (p-1)(q-1)
Public key:  (n, e)  where gcd(e, φ(n)) = 1  [e = 65537 is standard]
Private key: (n, d)  where e·d ≡ 1 (mod φ(n))

-- Encrypt --    C = M^e mod n
-- Decrypt --    M = C^d mod n

Security: Factoring n into p and q is computationally infeasible for large n.

✍️ Digital Signature Algorithms Auth + Integrity

Digital signatures provide authentication, integrity, and non-repudiation. The signer uses their private key to sign; anyone with the public key can verify. 

Sign:   signature = Sign(privateKey, hash(message))
Verify: valid     = Verify(publicKey, message, signature)

💡

Ed25519 vs ECDSA: Ed25519 (EdDSA) is deterministic — it never needs a random nonce, eliminating the catastrophic failure mode of ECDSA where reusing a nonce leaks the private key (the PS3 hack). Ed25519 is also faster to sign/verify.

Hash Functions Used with Signatures

SHA-256 ✓

32-byte output. Used with RSA-PSS, ECDSA P-256. Standard for TLS certificates and most JWTs.

SHA-384 ✓

48-byte output. Used with ECDSA P-384. Required for Suite B / NSA approved crypto.

SHA-512 ✓

64-byte output. Used with RSA-PSS PS512. Strong, but slower on 32-bit systems.

SHA-1 ✗

Collision attacks demonstrated (SHAttered 2017). Banned in TLS 1.3 certificates.

MD5 ✗

Completely broken — collisions trivially computed. Never use for security purposes.

📈 Elliptic Curve Cryptography (ECC) Compact & Fast

ECC exploits the algebraic structure of elliptic curves over finite fields. The security relies on the Elliptic Curve Discrete Logarithm Problem (ECDLP): given points G and Q = k·G, it's computationally infeasible to find k.

A 256-bit ECC key provides comparable security to a 3072-bit RSA key — dramatically smaller keys, faster operations, and less bandwidth.

Curve25519 advantages: Designed to avoid potential NIST backdoors (concerns raised post-Snowden), constant-time implementation by construction (side-channel resistant), and the math is simpler and faster. Used in TLS 1.3 as x25519 for ECDHE key exchange.

ECC Algorithms Built on Curves

ECDH / ECDHE

Key agreement. The E in ECDHE means ephemeral — a new key per session, providing forward secrecy. Used in TLS 1.3.

ECDSA

Elliptic Curve Digital Signature Algorithm. Requires a secure random nonce. Used in TLS certificates, JWT ES256/384/512, Bitcoin.

EdDSA (Ed25519)

Edwards-curve Digital Signature Algorithm. Deterministic — no random nonce needed. Faster, safer, and smaller signatures than ECDSA.

X25519

DH key exchange on Curve25519. Preferred TLS 1.3 key exchange method. NamedGroup: x25519 in TLS extension.

🤝 Diffie-Hellman Key Exchange Key Agreement

Diffie-Hellman (DH), published in 1976, was the first practical public-key protocol. It allows two parties to establish a shared secret over an insecure channel without any prior shared information. Neither party transmits the secret — they each contribute to computing it.

Classical DH — How It Works

Public parameters:  p (large prime),  g (generator)  ← shared openly

Alice:  a  = random private integer
        A  = g^a mod p   ← sends to Bob

Bob:    b  = random private integer
        B  = g^b mod p   ← sends to Alice

Alice computes:  S = B^a mod p  = g^(ba) mod p
Bob computes:    S = A^b mod p  = g^(ab) mod p

S is the same shared secret — but neither a nor b was transmitted.
🧑 Alice
Private: a
Sends: A = ga mod p
Computes: S = Ba mod p
⇄ A, B exchanged over insecure channel
🧑‍💻 Bob
Private: b
Sends: B = gb mod p
Computes: S = Ab mod p
= Shared Secret S gab mod p
✅ Shared
S = gab mod p
Same on both sides
Never transmitted

Forward Secrecy (Perfect Forward Secrecy)

When using ephemeral keys (DHE / ECDHE), a unique DH key pair is generated for every session. Even if the server's long-term private key is later compromised, past sessions cannot be decrypted because the ephemeral keys were discarded.

⚠️

Logjam Attack (2015): Classical DH using 512-bit or 1024-bit groups can be broken via precomputation. Use DHE with 2048-bit groups (ffdhe2048) or prefer ECDHE with X25519.

ECDHE in TLS 1.3 — The Math

-- Client --                                   -- Server --
Generate ephemeral keypair:                    Generate ephemeral keypair:
  client_private = random scalar a               server_private = random scalar b
  client_public  = a × G  (on the curve)         server_public  = b × G

Send client_public in ClientHello KeyShare  →
                                             ←  Send server_public in ServerHello KeyShare

Shared Secret:  S = a × server_public             S = b × client_public
                  = a × (b × G)                     = b × (a × G)
                  = (ab) × G   ← same point on curve for both

S → HKDF → {client_handshake_key, server_handshake_key, ...}

🌐 TLS 1.3 — Algorithms in Practice Current Standard

TLS 1.3 (RFC 8446, 2018) drastically simplified the protocol by removing weak algorithms and mandating forward secrecy. It uses ECDHE for key exchange, ECDSA/RSA/Ed25519 for authentication, and AES-GCM / ChaCha20-Poly1305 for record encryption.

TLS 1.3 Cipher Suites

Cipher SuiteAEAD CipherHash (HKDF)Notes
TLS_AES_128_GCM_SHA256 AES-128-GCM SHA-256 Default — mandatory to implement
TLS_AES_256_GCM_SHA384 AES-256-GCM SHA-384 High security
TLS_CHACHA20_POLY1305_SHA256 ChaCha20-Poly1305 SHA-256 Preferred for mobile / no AES-NI
TLS_AES_128_CCM_SHA256 AES-128-CCM SHA-256 IoT / constrained environments

Note: Key exchange (x25519, secp256r1) and signature algorithm (ECDSA, RSA-PSS, Ed25519) are negotiated separately as extensions — they are not part of the cipher suite string in TLS 1.3.

TLS 1.3 Handshake Flow

1
Client → ClientHello

Sends: supported cipher suites, TLS version, key_share (ephemeral ECDHE public key for x25519/P-256), signature_algorithms, supported_groups

2
Server → ServerHello

Sends: chosen cipher suite, own key_share (ephemeral ECDHE public key). Both sides now compute the shared secret → derive handshake keys via HKDF.

3
Server → {EncryptedExtensions + Certificate + CertificateVerify + Finished}

All encrypted with handshake key. CertificateVerify contains a digital signature (RSA-PSS, ECDSA, or Ed25519) over the handshake transcript — proves server owns the private key matching the cert.

4
Client → {Certificate (if mutual TLS) + CertificateVerify + Finished}

Client verifies server cert chain → derives application traffic keys from HKDF. Finished messages use HMAC to verify the entire handshake transcript.

5
Application Data (encrypted)

All data encrypted with AES-GCM or ChaCha20-Poly1305 using the derived application keys. Each record has a unique nonce derived from the sequence number + IV.

What Each Algorithm Does in TLS 1.3

ECDHE (X25519 / P-256)

Key Exchange. Establishes the shared secret. Ephemeral keys ensure forward secrecy — old sessions safe even if server key is compromised.

ECDSA / RSA-PSS / Ed25519

Authentication. Server (and optionally client) proves identity via signature in CertificateVerify. Prevents MITM attacks.

HKDF (with SHA-256/384)

Key Derivation. Derives multiple symmetric keys from the ECDHE shared secret: handshake keys, application keys, resumption secrets.

AES-128/256-GCM

Record Encryption. Encrypts + authenticates application data with AEAD. Prevents eavesdropping and tampering.

ChaCha20-Poly1305

Alternative AEAD. Software-efficient cipher for devices without AES hardware acceleration. Used in mobile TLS and QUIC.

X.509 Certificates

PKI / Trust Anchor. Bind the server's public key to its identity, signed by a trusted Certificate Authority.

✅

Removed in TLS 1.3: RSA key exchange, static DH/ECDH, RC4, DES, 3DES, MD5/SHA-1 in certs, CBC mode ciphers, compression, renegotiation. The protocol surface is now minimal and secure by default.

⚛️ Post-Quantum Cryptography (PQC) NIST 2024 Standards

A sufficiently powerful quantum computer running Shor's algorithm can break all RSA, DH, ECDH, and ECDSA — any algorithm based on integer factorization or discrete logarithms. Grover's algorithm halves the effective key length of symmetric ciphers (AES-256 → 128-bit security). Post-quantum algorithms are designed to resist both classical and quantum attacks.

☢️

"Harvest now, decrypt later" threat: Adversaries are collecting encrypted traffic today, planning to decrypt it once quantum computers mature. For long-lived sensitive data, PQC migration is urgent now — not later.

NIST PQC Standards (Finalized 2024)

ML-KEM — FIPS 203 (formerly CRYSTALS-Kyber)

Type: Key Encapsulation Mechanism (KEM) — replaces ECDH / RSA key exchange

Security basis: Module Learning With Errors (MLWE) — lattice-based hard problem

Variants: ML-KEM-512 (~128-bit), ML-KEM-768 (~192-bit), ML-KEM-1024 (~256-bit)

Performance: Fast — comparable to ECDH. Public key: ~1184 B. Ciphertext: ~1088 B (ML-KEM-768)

Use cases: TLS 1.3 key exchange (hybrid X25519+ML-KEM), Signal Protocol, VPN, SSH

NIST Standard TLS Hybrid Proposed Lattice

ML-DSA — FIPS 204 (formerly CRYSTALS-Dilithium)

Type: Digital Signature — replaces ECDSA / RSA-PSS

Security basis: Module Learning With Errors (MLWE) — lattice-based

Variants: ML-DSA-44 (~128-bit), ML-DSA-65 (~192-bit), ML-DSA-87 (~256-bit)

Performance: Fast signing and verification. Sig size: ~2420–4595 B (larger than ECDSA's 64 B)

Use cases: TLS 1.3 certificate signatures, code signing, document signing, PKI

NIST Standard Lattice

SLH-DSA — FIPS 205 (formerly SPHINCS+)

Type: Digital Signature — hash-based, conservative choice

Security basis: Security of SHA-256 / SHAKE256 hash functions only

Variants: SLH-DSA-SHA2-128s/f, SLH-DSA-SHAKE-256s/f (s=small sigs, f=fast)

Performance: Slow signing (esp. -s variants). Sig size: 7856–49856 B. Verification is fast.

Use cases: Long-lived root CA certificates, firmware signing, cases requiring conservative security assumptions

NIST Standard Hash-based Conservative

FN-DSA — FIPS 206 (formerly Falcon)

Type: Digital Signature — compact lattice-based

Security basis: NTRU lattice, Short Integer Solution (SIS) problem

Variants: Falcon-512 (~128-bit), Falcon-1024 (~256-bit)

Performance: Very compact signatures (690 B / 1330 B) — much smaller than Dilithium

Use cases: Bandwidth-constrained environments, IoT, blockchain, smart cards

NIST Standard NTRU Lattice Compact

Hybrid TLS: Classical + Post-Quantum

During the transition, hybrid key exchange combines a classical algorithm (e.g., X25519) with a PQC algorithm (ML-KEM-768). Both are run; the shared secrets are combined. Security holds if either algorithm remains unbroken. 

-- TLS 1.3 Hybrid Key Exchange --
Client sends KeyShare:
  X25519 public key  +  ML-KEM-768 public key  (in key_share extension)

Server responds:
  X25519 public key  +  ML-KEM-768 ciphertext

Both sides compute:
  SS_classical = X25519(priv, peer_pub)
  SS_pqc       = ML-KEM-768.Decaps(priv, ciphertext)
  shared_secret = HKDF-Expand(SS_classical || SS_pqc)

Named group: X25519MLKEM768 (IANA assigned, RFC draft)
🚀

Deployed today: Google Chrome, Cloudflare, and AWS already support X25519MLKEM768 hybrid key exchange in production TLS. Go 1.23+ enables it by default. OpenSSL 3.5+ adds ML-KEM support.
