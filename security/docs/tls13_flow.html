TLS 1.3 — Complete End-to-End Flow

How your browser and server establish a secure, authenticated, encrypted channel in just 1 round-trip.

🔑 Key Exchange

Ephemeral Diffie-Hellman (ECDHE / DHE) only. RSA key transport is removed — guaranteeing forward secrecy for every connection.

🛡️ Authentication

Server proves identity via an X.509 certificate chain signed with RSA or ECDSA. Client optionally authenticates too (mutual TLS).

⚡ Performance

Full handshake completes in 1-RTT (vs 2-RTT in TLS 1.2). Resumed sessions can send data in 0-RTT.

🧹 Simplified Design

Removed insecure algorithms (RC4, 3DES, SHA-1, static RSA, CBC-mode ciphers, compression). Only 5 cipher suites remain.

TLS 1.3 Cipher Suites

How Cipher Suite Selection Works

In TLS 1.3, cipher suites only specify the symmetric encryption + hash. Key exchange (always ECDHE/DHE) and signature algorithms are negotiated separately via extensions.

  1. Client sends a list of supported cipher suites in ClientHello, ordered by preference.
  2. Client also sends supported_groups (e.g. x25519, secp256r1) and signature_algorithms (e.g. ecdsa_secp256r1_sha256) extensions.
  3. Server picks one cipher suite from the intersection, respecting its own preference order.
  4. Server independently selects a key-share group and signature algorithm.
  5. If no common cipher suite exists → handshake_failure alert.

The 5 Defined Cipher Suites

TLS_AES_128_GCM_SHA256
AES-128 in GCM mode, SHA-256 — most widely used
TLS_AES_256_GCM_SHA384
AES-256 in GCM mode, SHA-384 — higher security margin
TLS_CHACHA20_POLY1305_SHA256
ChaCha20-Poly1305, SHA-256 — fast on mobile/ARM (no AES-NI)
TLS_AES_128_CCM_SHA256
AES-128 in CCM mode — for constrained IoT devices
TLS_AES_128_CCM_8_SHA256
AES-128 CCM with 8-byte tag — minimal IoT overhead

e.g., DigiCert SHA2 Extended Validation Server CA

Leaf / End-Entity Certificate
e.g., CN=www.example.com

Contains server's public key · Signed by Intermediate CA

Server Authentication Steps

  1. Certificate message: Server sends leaf cert + intermediates (encrypted under handshake keys).
  2. CertificateVerify message: Server signs a hash of the entire handshake transcript with its private key.
  3. Client validates:
    • Certificate chain → trusted root CA
    • Hostname matches cert's SAN/CN
    • Certificate not expired / not revoked (OCSP)
    • CertificateVerify signature valid (proves server holds private key)
  4. Finished message: Server sends HMAC over entire transcript — confirms it derived the same keys.

Why CertificateVerify Matters

In TLS 1.2, the server's RSA key exchange implicitly proved key ownership. Since TLS 1.3 uses only ephemeral DH, the server must explicitly prove it owns the certificate's private key by signing the handshake transcript.


Signature Algorithms (negotiated separately)

  • ecdsa_secp256r1_sha256
  • ecdsa_secp384r1_sha384
  • rsa_pss_rsae_sha256
  • rsa_pss_rsae_sha384
  • ed25519 / ed448

0-RTT Session Resumption

How 0-RTT Works

  1. After a previous handshake, the server sent a NewSessionTicket containing a PSK (Pre-Shared Key).
  2. On reconnection, the client includes the PSK in ClientHello along with early data (encrypted with keys derived from PSK).
  3. Server decrypts early data immediately — no round-trip wait.
  4. Handshake continues as normal (1-RTT) to establish fresh keys for the rest of the session.

⚠️ 0-RTT Security Considerations

  • No forward secrecy for 0-RTT data (derived from PSK, not fresh ECDHE).
  • Replay attacks possible: an attacker can capture and resend 0-RTT data. Servers must implement replay protection.
  • Only safe for idempotent requests (e.g., GET). Never for state-changing operations (POST, payment).
  • Server can reject 0-RTT by not decrypting early data → falls back to normal 1-RTT.

How Data Is Encrypted After Handshake

Record Layer Structure

┌─────────────────────────────────┐
│  ContentType (1 byte)           │  = 0x17 (Application Data)
│  Legacy Version (2 bytes)       │  = 0x0303
│  Length (2 bytes)                │
├─────────────────────────────────┤
│                                 │
│  Encrypted Payload              │
│  ┌───────────────────────────┐  │
│  │ Actual content type       │  │
│  │ Plaintext data            │  │
│  │ Padding (optional)        │  │
│  └───────────────────────────┘  │
│                                 │
│  Authentication Tag (16 bytes)  │
└─────────────────────────────────┘

AEAD Encryption Process

  • Key: derived from traffic secret via HKDF-Expand-Label
  • IV: derived similarly, XORed with record sequence number
  • AAD: record header (content type + version + length)
  • Plaintext: actual content + real content type + padding
  • Output: ciphertext + 16-byte authentication tag

Key Update

Either side can send a KeyUpdate message to rotate traffic keys without a new handshake. New keys are derived from the current traffic secret using HKDF-Expand-Label.
