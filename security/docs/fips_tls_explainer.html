1. What is FIPS 140-3?

FIPS 140-3 (Federal Information Processing Standard) is a US government standard that defines approved cryptographic algorithms and key sizes. Any system handling sensitive federal data must use only FIPS-validated modules.

FIPS-Approved ✓

CategoryApproved
SymmetricAES-128, AES-256 (GCM, CBC)
HashingSHA-256, SHA-384, SHA-512
AsymmetricRSA ≥ 2048, ECDSA P-256/P-384
Key ExchangeECDHE (P-256, P-384), DHE
TLS VersionsTLS 1.2, TLS 1.3

NOT FIPS-Approved ✗

CategoryRejected
SymmetricRC4, DES, 3DES, ChaCha20
HashingMD5, SHA-1
AsymmetricRSA < 2048, Ed25519
Key Exchangex25519 (Curve25519)
TLS VersionsTLS 1.0, TLS 1.1, SSL 3.0

3. PostgreSQL SSL Configuration

These settings are active in postgresql.conf:

ssl                    = on
ssl_cert_file          = 'server.crt'
ssl_key_file           = 'server.key'
ssl_ca_file            = 'root.crt'
ssl_min_protocol_version = 'TLSv1.2'
ssl_ciphers            = 'HIGH:MEDIUM:+3DES:!aNULL'   ← OpenSSL cipher string

How to check what ciphers PostgreSQL actually supports

Run this in psql to list active cipher suites the server will accept:

-- Shows currently negotiated cipher for YOUR session
SELECT ssl, version, cipher, bits
FROM pg_stat_ssl
WHERE pid = pg_backend_pid();

To list all ciphers the OpenSSL string HIGH:MEDIUM:+3DES:!aNULL expands to:

openssl ciphers -v 'HIGH:MEDIUM:+3DES:!aNULL' | sort

To restrict PostgreSQL to only FIPS-approved suites, change postgresql.conf:

ssl_ciphers = 'ECDHE-RSA-AES128-GCM-SHA256:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384'
ssl_min_protocol_version = 'TLSv1.2'

4. Go TLS Config Explained

tlsConfig := &tls.Config{
    MinVersion:   tls.VersionTLS12,
    MaxVersion:   tls.VersionTLS12,       // pin to TLS 1.2 to see cipher negotiation in Wireshark
    ServerName:   "localhost",            // must match CN or SAN in server.crt
    RootCAs:      caCertPool,             // CA cert — used to verify PostgreSQL's server.crt
    Certificates: []tls.Certificate{     // client cert — sent to PostgreSQL for mTLS
        clientCert,
    },
    CipherSuites: []uint16{              // explicit FIPS-only list (omit to use Go defaults)
        tls.TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,
        tls.TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384,
        tls.TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256,
        tls.TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384,
    },
    CurvePreferences: []tls.CurveID{
        tls.CurveP256,   // FIPS-approved
        tls.CurveP384,   // FIPS-approved
        // x25519 deliberately omitted — NOT FIPS-approved
    },
}
FieldWhy it matters
ServerNameGo verifies the server cert's CN/SAN matches this. Without it, the TLS handshake fails with "either ServerName or InsecureSkipVerify must be specified".
RootCAsTells Go to trust only your internal CA instead of the system root store. Prevents accepting certs from public CAs.
CertificatesThe client cert sent to PostgreSQL during mTLS. PostgreSQL verifies it against root.crt.
CipherSuitesWhen set, Go advertises ONLY these in the Client Hello. When omitted, Go advertises its full default list (incl. ChaCha20, x25519).
Fallbacks = nilPrevents pgx from silently retrying with plaintext if TLS fails. Without this, a failed TLS negotiation returns a working but unencrypted connection.

5. FIPS vs Non-FIPS: Side-by-Side

Non-FIPS mode (default)

go run main_postgres_tls.go

PropertyValue
Client Hello cipher suitesAll Go defaults: AES-GCM + ChaCha20-Poly1305
Supported groups (curves)x25519, P-256, P-384, P-521
Signature algorithmsEd25519 allowed
RSA minimum key sizeNot enforced by Go
TLS versionTLS 1.2 or 1.3 (whatever server prefers)
FIPS moduleStandard Go crypto

Note With CipherSuites explicitly set in code (as in this project), ChaCha20 is excluded regardless of FIPS mode — because you hard-coded the list.

FIPS 140-3 mode

GODEBUG=fips140=only go run main_postgres_tls.go

PropertyValue
Client Hello cipher suitesOnly AES-GCM suites (ChaCha20 stripped)
Supported groups (curves)Only P-256, P-384 (x25519 removed)
Signature algorithmsEd25519 rejected
RSA minimum key size≥ 2048 bits enforced
TLS versionTLS 1.2 minimum enforced
FIPS moduleGo's internal FIPS 140-3 crypto module

Compliant All cryptographic operations use validated algorithms. Non-approved operations panic or return errors.

How to see the actual difference in Wireshark

Step 1 — Run without FIPS (with CipherSuites commented out) 
go run main_postgres_tls.go

In Client Hello you will see:

  • TLS_CHACHA20_POLY1305_SHA256
  • TLS_ECDHE_RSA_WITH_CHACHA20_POLY1305_SHA256
  • x25519 in Supported Groups
Step 2 — Run with FIPS (with CipherSuites commented out) 
$env:GODEBUG="fips140=only"
go run main_postgres_tls.go

In Client Hello you will see:

  • NO ChaCha20 suites
  • NO x25519 in Supported Groups
  • Only AES-GCM + P-256/P-384

6. TLS 1.2 Handshake Flow (mutual TLS)

What happens on the wire when go run main_postgres_tls.go connects:

  1. TCP SYN / SYN-ACK / ACK — standard 3-way TCP handshake to port 5432.
  2. PostgreSQL SSLRequest (8 bytes: 00 00 00 08 04 D2 16 2F)
    The Go client sends this before the TLS Client Hello. It's a PostgreSQL-specific probe asking "do you support TLS?"
  3. Server responds S — single byte meaning SSL/TLS is supported. (If the server responds N, TLS is disabled on the server — the bug we fixed by enabling ssl=on.)
  4. Client Hello — Go sends TLS Client Hello containing:
    • Supported cipher suites (your 4 FIPS suites, or Go's full list)
    • Supported groups: P-256, P-384 (FIPS) or also x25519 (non-FIPS)
    • Random 32 bytes (nonce)
    • Session ID
  5. Server Hello — PostgreSQL picks the strongest mutually supported cipher suite and responds with:
    • Selected cipher suite (e.g. TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384)
    • Server random nonce
  6. Certificate — PostgreSQL sends server.crt. Go verifies: signed by ca.crt? CN/SAN = "localhost"? Not expired?
  7. CertificateRequest — Because ssl_ca_file is set in PostgreSQL, it requests a client certificate (mutual TLS).
  8. ServerHelloDone — server signals it's done with its part of the negotiation.
  9. Client Certificate — Go sends client.crt. PostgreSQL verifies: signed by root.crt? Not expired?
  10. ClientKeyExchange + CertificateVerify — ECDHE key exchange; client proves ownership of the private key by signing the handshake transcript.
  11. ChangeCipherSpec + Finished (both sides) — session keys derived; handshake authenticated. All subsequent data is encrypted with AES-GCM.
  12. PostgreSQL StartupMessage — now inside the TLS tunnel, the normal PostgreSQL wire protocol begins (user/database/params).

8. PostgreSQL Cipher Support

PostgreSQL uses OpenSSL for TLS, not Go's crypto. Its cipher list is configured via ssl_ciphers in postgresql.conf using OpenSSL cipher string syntax.

Current config: HIGH:MEDIUM:+3DES:!aNULL

This is PostgreSQL's default. It accepts many suites including 3DES (not FIPS-approved). For strict FIPS compliance, restrict it:

Cipher suiteOpenSSL nameFIPS?
TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256ECDHE-RSA-AES128-GCM-SHA256Yes
TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384ECDHE-RSA-AES256-GCM-SHA384Yes
TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256ECDHE-ECDSA-AES128-GCM-SHA256Yes
TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384ECDHE-ECDSA-AES256-GCM-SHA384Yes
TLS_ECDHE_RSA_WITH_CHACHA20_POLY1305_SHA256ECDHE-RSA-CHACHA20-POLY1305No
TLS_RSA_WITH_AES_256_CBC_SHA256AES256-SHA256TLS 1.2 only, no PFS
TLS_RSA_WITH_3DES_EDE_CBC_SHADES-CBC3-SHANo (3DES)

To make PostgreSQL FIPS-only, set in postgresql.conf:

ssl_ciphers              = 'ECDHE-RSA-AES128-GCM-SHA256:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384'
ssl_min_protocol_version = 'TLSv1.2'

Then reload: SELECT pg_reload_conf(); (no restart needed for cipher changes).

Verify the negotiated cipher after connection:

SELECT pid, ssl, version, cipher, bits, client_dn
FROM pg_stat_ssl
WHERE pid = pg_backend_pid();
