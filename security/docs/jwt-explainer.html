How JWT Works

Access tokens · Refresh tokens · HMAC signing · Stateless auth

1 — JWT Structure

A JWT is three Base64URL-encoded JSON objects joined by dots. Nothing is encrypted — it is signed, so the server can detect tampering.

Header
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.
Payload
eyJ1c2VybmFtZSI6InRlc3R1c2VyIiwiZXhwIjoxNzU0MDAwMDAwfQ
.
Signature
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
Header (decoded)
{
  "alg": "HS256",
  "typ": "JWT"
}
Payload / Claims (decoded)
{
  "username": "testuser",
  "iat": 1754000000,
  "exp": 1754000030
}
Signature
HMACSHA256(
  base64(header) +
  "." +
  base64(payload),
  SECRET
)

The payload is readable by anyone — never store passwords or secrets in it. The signature is what makes it trustworthy: only the server holding the secret key can produce or verify it.

2 — HMAC-SHA256 Signing

HMAC (Hash-based Message Authentication Code) uses a shared secret to both sign and verify a message. HS256 means HMAC with SHA-256.

Signing (at login):

base64(header) + "." + base64(payload)
+
SECRET KEY
→
SHA-256 hash function
→
Signature

Verification (on every request):

Re-compute HMAC of incoming header + payload
==?
Incoming signature
✅ If they match — the payload was not tampered with and was issued by someone who knows the secret.
❌ If they differ — the payload was modified (e.g. someone changed exp to extend the token) — request is rejected.
⚠️ HS256 is symmetric — the same key signs and verifies. In a multi-service setup use RS256 (asymmetric) so only the auth server holds the private key.

3 — Access Token vs Refresh Token

Access TokenRefresh Token
PurposeProve identity on each API callGet a new access token without re-login
TTLShort — 15 min (30 s in test)Long — 7 days (2 min in test)
Sent toEvery protected API endpointOnly /refresh
Stored asHttpOnly; Secure; SameSite=Strict cookieSame — scoped to Path=/refresh
If stolenAttacker has access for at most 15 minAttacker can keep refreshing — guard it tightly
Revocable?No (stateless)Yes (server-side store)

The short access token TTL limits blast radius. Even if an access token leaks, it's useless within minutes. The refresh token is only ever sent to one endpoint and is rotated on every use.

Token rotation — every POST /refresh invalidates the old refresh token and issues a new one. If the old token is used again, the server detects reuse and rejects it.

5 — Full Auth Flow

POST /login
Client sends username + password. Server validates, generates access + refresh tokens, sets both as HttpOnly cookies. Redirects to /profile.
GET /api/profile (protected)
Browser automatically sends the access_token cookie. Middleware validates the JWT signature and expiry. If valid, injects username into request context.
token_expiring_soon: true
Server sees the token expires within 3 minutes and includes this flag in the JSON response. The client JS calls POST /refresh proactively — user never notices.
POST /refresh
Browser sends the refresh_token cookie (scoped to this path only). Server validates it, checks the in-memory store, generates a new pair, sets new cookies, and invalidates the old refresh token.
Access token expired, refresh also expired
/api/profile returns 401. Client redirects to /login. User must authenticate again.

6 — Why Stateless?

Traditional session-based auth stores a session ID in a database. Every request requires a DB lookup to check if the session is valid. JWT flips this:

Session (stateful)JWT (stateless)
Server storesSession record in DB / RedisNothing (only the signing secret)
Verification costDB round-trip on every requestCPU-only HMAC verification
Horizontal scalingAll servers share the same session storeAny server can verify — no shared state
RevocationInstant — delete session rowMust wait for expiry (or use a deny-list)
Works across servicesSession store must be accessibleAny service with the public key can verify
✅ Stateless = the token itself is the proof of identity. The server trusts the math, not a database record.
⚠️ The tradeoff: you cannot instantly revoke an access token. Short TTLs (15 min) + refresh token rotation are the standard mitigations.
